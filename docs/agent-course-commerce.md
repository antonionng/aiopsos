# Agent course purchase and enrolment

The checkout implementation is controlled by `AGENT_COURSE_COMMERCE_ENABLED=true`. Commerce, Stripe and AI assessment migrations are installed in the app's `aiopsos` Supabase project. On 2 October 2026, all 13 authored agent courses were registered with published content versions, frozen learning packs, internal template programmes and six-skill assessment plans. The owner subsequently requested opening checkout using the existing Stripe connection. All 13 offers are active at £99 GBP, their plans are released, and the production feature flag is enabled. An authenticated fictional learner opened a live-mode Stripe Checkout session at £99. A repeated request returned the same order and session; unpaid learning access returned 403. No card details were entered and no payment was made. The synthetic account was suspended and banned and its pending order voided after verification. A successful real purchase and fulfilment remain unverified.

## What has been built

- Course offers connect a marketing slug to an existing published LMS version and an internal template programme. The price is £99 in GBP and comes from the server, never the browser.
- A signed-in learner with an active organisation membership accepts the offer's current terms version before checkout. The existing platform currently requires a learning workspace; this is not anonymous guest checkout.
- Reserving an order grants no learning access. Retries and a second tab return the same pending payment request. An existing paid order opens its learning assignment.
- Stripe Checkout supplies the secure payment page. The internal order reference is its idempotency key, and payment metadata links Checkout and refund events to the stored order. Existing Mooov orders retain their callback handler.
- A verified course payment webhook creates the order receipt, copied programme, frozen course version, assessment plan, accepted delivery staff and learner assignment in one PostgreSQL transaction. Failures roll back the receipt so the same event can be retried. Returning to the success page never grants access by itself.
- An owned order-status endpoint checks both the learner and their current workspace. The return page waits for payment confirmation and then links to the existing learning workspace.
- A full refund archives the purchased programme while preserving its learning record and evidence, unless another captured payment still funds the same assignment. Historical records remain readable; further practical work is paused. A delayed capture cannot reopen a refunded order. Partial refunds do not change enrolment.

Course order references start with `pay_course_` for historical compatibility; `payment_provider` identifies the processor. New orders use Stripe. The verified Stripe webhook sends course events to the transactional course handler. Existing Mooov orders retain their old callback path; the Mooov webhook ignores Stripe orders. If separate attempts both capture out of order, both payment records are retained and the same course/version assignment is reused. Operations must reconcile and refund any duplicate charge; the handler does not automatically initiate a refund.

## Preparing an offer

1. In Course Studio, load the authored pack, inspect it, save a draft and publish the reviewed version. Verify illustrations and practical resources in the actual learner interface.
2. Create an internal template programme using only that course version. Keep its client organisation empty. Prepare its assessment plan. AI offers use the dedicated project assessor and do not require an accepted human reviewer; human-assessed offers still require accepted reviewer access. The reserve-order function refuses mismatched versions, unreleased plans and provider accounts attempting consumer checkout.
3. Confirm the assessment plan implements the course standard: a minimum score of 3 out of 4 in every required skill area, feedback and resubmission, rather than an overall average compensating for a weak area. The course rubric and the existing LMS weighted scoring are not automatically equivalent. Keep `assessment_ready=false` until this is verified.
4. Review and publish the course purchase terms, including what is included, platform/account prerequisites, access arrangements, assessment service, cancellations and refunds. Store the actual terms URL and a version identifier in the offer. The implementation does not invent or publish these commercial terms.
5. Create the offer using the published version ID and template programme ID. Offers default to inactive and assessment not ready. Administrators manage offers through the service-side database workflow; a release-management interface is not yet implemented.
6. Apply `supabase/migrations/20261001175409_agent_course_commerce.sql`, then `supabase/migrations/20261002094146_stripe_direct_payments.sql` through the project's migration workflow. Configure a secure `NEXT_PUBLIC_APP_URL`, `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`. See stripe-payments.md for webhook events and test/live configuration.
7. Test a complete signed-in purchase in the payment provider's test environment: return before the webhook, confirmed capture, duplicate delivery, database failure followed by retry, refund, changed workspace, and access attempts by another learner. Check the actual lesson, submission, reviewer and certificate workflows. Isolated database tests do not replace this check.
8. Mark the reviewed offer active and assessment ready, release its plan and enable the feature flag when launch is authorised. Public detail pages, the catalogue and the homepage read live offer availability. Record the scope of verification accurately: the owner requested launch using the existing Stripe connection, while a complete real-card purchase remains unverified.

## Verification

`lib/always-on-agents/commerce.test.ts` runs the actual commerce migration in isolated PostgreSQL using PGlite and the repository's LMS tables, membership guard and delivery-role function. It checks server pricing, current terms, active membership, release readiness, idempotent orders, confirmed enrolment, access boundaries, rollback/retry, refunds and browser-role denial. `lib/__tests__/stripe-payments.test.ts` checks Checkout metadata, stored pricing, unpaid sessions, refunds and webhook retry responses using SDK fixtures. `lib/__tests__/stripe-transactions.test.ts` checks credit and cohort fulfilment in isolated PostgreSQL. These tests send no payments.

All three migrations are installed on the deployed Supabase project, with their columns, service-only function permissions and table security verified. The AI assessment workflow implements certificate issuance and requires at least 3/4 in every skill. This does not replace a complete deployed payment and learning flow test. Checkout itself issues no certificates. See stripe-payments.md for the remote migration versions and the existing CLI project-link mismatch.

## Registering the authored courses

`scripts/register-agent-courses.mts` validates the configured project hostname and an explicit platform author, then checks the author's current workspace permissions. The default run validates without writing; `--apply` adds the courses, versions, template programmes, unreleased delivery plans and inactive AI offers. Existing matching offers are retained. Content differences stop registration so a published version cannot silently change. The author's existing workspace is used without renaming it or altering their membership. No reviewer acceptance, payment, assessment result or certificate is created.

Supply `--project=<verified-project-ref>` and `--actor=<verified-platform-author-id>` with local server credentials. Do not use the stale CLI-linked project. Registration may be resumed after interruption: it checks the matching draft, version, programme and plan before adding a missing record. Run only one registration process at a time.

Assessment coverage is checked in `lib/__tests__/course-assessment-coverage.test.ts`. All 40 existing self-paced courses have scenario assessments, answer feedback and a final practical document; all 13 agent courses have practical projects and the six-area AI assessment policy. Existing self-paced course progress is now re-evaluated from answers on the server, and issued work is retained unchanged on subsequent saves. The two assessment methods are distinct; existing self-paced courses are not described as having AI-reviewed projects.

Official integration reference: [Stripe Checkout fulfilment](https://docs.stripe.com/checkout/fulfillment).

Completed assessments create an email outbox record in the same database transaction. The report includes scores, feedback, next steps, cited extracts and assessment limits. Immediate delivery runs after the response; the protected report cron retries pending reports every ten minutes within the email provider's idempotency window. After that window the record stays available for operational review, and the learner can still download it. Submission text is not included in the public certificate.
