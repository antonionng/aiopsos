# Wonderlab: learning inside a playable world

Design revision: 9 October 2026. This is the replacement design brief for all 24 missions, not a claim that all 24 replacements are built. The first implemented slice is the courier world and contextual guide. Existing purchases, profiles and saved work remain valid.

## The problem we are solving

The current catalogue has too many selections followed by a result panel, repeated mechanics under different names, and introductory text that carries the explanation the game should demonstrate. The learner sometimes constructs a route and then manually performs it, which creates an unnecessary second interaction. The visual treatment looks like a board with tokens rather than a place where something matters. Older learners have little room for a personal solution. Mandatory written reflections interrupt the reward immediately after success.

Some lesson mappings also need correction. A fixed route builder can introduce instructions and testing, but it does not itself teach prompting a language model. A scheduling puzzle cannot carry the whole Brief Builder outcome. An evidence interface is useful, but should not stand in for every privacy, study and investigation game.

## The experience standard

A child arrives in an animated place with a visible problem and an immediate action. They manipulate something meaningful, watch the consequence, investigate a mismatch and revise their idea. The world changes when their solution works. Pip helps at the moment of uncertainty. The next challenge changes a requirement so copying the previous solution is insufficient.

Keep one current objective and one primary action. Within ten seconds, the learner should be able to start without reading a page. Introduce one tool at a time with a playable demonstration. Avoid separate build, fabricate, enter-world and walk modes. When a child designs a system, let that system run automatically; direct character control belongs in exploration games where movement reveals information.

The game world should occupy most of the play area. Use animated characters with distinct poses, layered environments, transitions that show cause and effect, and objects that visibly respond. Keep written evidence readable where it genuinely matters. Use clear pause, replay, sound and reduced-motion controls. Maintain equivalent keyboard and touch controls, with a useful accessible description of world state. No countdown is necessary for learning; any timed replay is optional.

A reward is a change the child caused: a garden grows, a creature reaches its habitat, a show opens, or a publication becomes trustworthy. Stickers and a private collection supplement that consequence. Avoid streak penalties, public rankings and purchases during play. Let children keep their creation before an optional reflection; require a fresh practical challenge for learning completion. A hint-supported result and an independent transfer result must be distinguishable in parent insights.

## Pip teaches during play

Pip is a fictional guide, not a friend or an authority that is always right. Give Pip a location and purposeful animations inside each world: looking at the object being tested, reacting to a failed bridge, or bringing over a source card. The current companion panel establishes the interaction contract; a character animation and world-integrated speech presentation should replace the panel as each new scene is authored.

Guidance is event-based: introduce the next action; notice a relevant change; ask a question after an unsuccessful test; offer a stronger hint only when requested; explain the learning connection at the moment it becomes visible; fade support for the fresh challenge. Allow the learner to pause and work without narration. Do not repeatedly interrupt, give away every answer or use praise unrelated to a specific decision.

For ages 4–10, use reviewed branching dialogue and authored voice. For ages 11–16, optional parent-enabled AI can phrase a short hint from a bounded, server-derived game context. It must not control the world, mark its own answers correct or invent rules. The simulation and server validators remain authoritative. Show prepared guidance and generated responses accurately. Reuse the existing moderation, retention gates, entitlements and successful-generation allowance. Do not send names, written reflections, private creations or unbounded chat to the model. The first implementation requests hints on demand rather than spending an allowance on every movement.

Example in Delivery Lab: the courier stops before the river. Pip says, “The route reaches the water but doesn't cross it. What could connect the two banks?” The learner adds a bridge and tests again. After delivery, Pip connects the experience to checking an AI-produced plan. The later AI proposal adds an unsupported claim so the child sees that precise instructions alone do not guarantee truth.

## Third-party production tools

**Recommended direction: Phaser for the production game layer, with AI-assisted authoring.** It is a browser game framework and has current visual-editor and AI-agent tooling. Its scene and animation model is better suited to layered worlds, sprites, particles and responsive input than expanding a page of form controls. Keep React for accessible instructions, family accounts, settings and collections. Keep assessment and ownership checks on Experrt's server. This recommendation is an engineering judgement, not evidence that changing engines alone makes a game enjoyable.

Phaser's own [Editor v5 announcement](https://phaser.io/news/2026/04/phaser-editor-v5-release) describes its AI integration, and its [Game Agent MCP guide](https://www.phaser.io/news/2026/07/phaser-game-agent-mcp-setup) describes integration with coding assistants. No new vendor account, paid plan or global tool installation has been made in this change.

**GDevelop is a credible alternative for designer-led production.** Its official [game-maker overview](https://gdevelop.io/game-makers) describes an AI agent, visual logic and HTML5 export for a site's own hosting. It is worth a short authoring trial if non-programmers will build and maintain the scenes. Verify the exported build's loading, accessibility and integration before choosing it.

**Rosebud is useful for a prototype comparison.** Its [official Three.js editor page](https://dev.play.rosebud.ai/ai-website-builder-three-js-editor) describes generated projects, embedding and full export on specified paid plans. Treat a generated prototype as source material to inspect. Confirm current export terms and an actual downloaded project's independence before committing production work to it.

Use generation during production for reviewed environment concepts, sprite variations, dialogue drafts, sound concepts and code scaffolding. Keep a consistent Pip character sheet, age-specific art bible and small animation library. Review generated assets for visual continuity and store the approved files with the product. Live generation is not required to make a child-facing world feel responsive. Avoid loading an unreviewed third-party game or its account, advertising or analytics services inside a child's session.

## Build and validation sequence

1. Finish and evaluate the courier vertical slice: an illustrated world, automatic tests, visible failures and useful guidance. It is a mechanics benchmark, not the final art quality bar or a complete replacement for Prompt Repair Shop.
2. Author one production-quality mission per age band: River Ride, Creature Expedition, Signal City Newsroom and Game Jam. Each gets a full playable introduction, meaningful practice, changed transfer challenge, animation and reward.
3. Observe families playing without developer explanations. Record whether they know the goal, can start, notice the consequence, revise deliberately, explain one AI connection and want another round. Record frustration and adult help. Do not claim enjoyment or learning impact before this test.
4. Build the remaining missions using validated systems. Share rendering, save, input and guidance infrastructure; do not copy the same learning puzzle into unrelated subjects.
5. Review the complete 24-game experience against parent-facing promises before calling the redesign complete. Preserve old work and explicitly migrate versioned progress when mechanics change.

Parent insights should describe observed practice: the type of task attempted, changes made after feedback, hints used and results on a new challenge. Include a concrete suggestion for a parent conversation. Avoid ranking intelligence, labelling a child as weak or claiming mastery from clicks or completion alone.

## Implementation in this pass

- The Forge family now uses an illustrated delivery landscape with an animated courier and automatic route tests. Missing connections are shown in place. A child edits the same world directly without a second walking mode.
- All 12 current older adventures receive a contextual Pip guide with prepared hints, an explanation of the AI connection and the existing OpenAI narration voice.
- Eligible signed-in older learners can request a short AI hint about their saved game step, using the existing server checks and allowance. This path still needs a full eligible-account provider test; demo mode uses prepared guidance.
- The existing data model, verified completion rules and rewards remain in place. The other proposed game replacements, integrated character acting, revised reward/reflection flow and wider art production are not implemented by this pass.
